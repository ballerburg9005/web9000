# WEB9000 comparative research — what to borrow from Nostr, what to avoid

**Research snapshot: 2026-11-19.** Primary sources are linked in-line. This is a design comparison, not evidence that WEB9000 is Nostr-compatible or that Nostr guarantees resistance to coordinated relay refusal.

## Short conclusion

**Borrow individual protocols and lessons, not Nostr's entire model.** Nostr demonstrates a useful split between portable signed data and replaceable relay hosts, with efficient selective retrieval, relay discovery, independent moderator labels and identity-controlled lists. Its more sophisticated later work helps with WEB9000's exact weak points. Yet neither relay selection, proof-of-work, nor being able to *fork* a relay-hosted group solves the core governance issue by itself. WEB9000's user explicitly rejected first-claimer community monopolies and the ability of a tiny relay-admin group to suppress competing publications.

## The three strongest directly actionable lessons

### 1. Replication must be **interest-scoped and reconcile missing IDs**

WEB9000 currently connects to selected browser bridges and asks for **all spaces**. That recreates a requirement to rely on one huge global log or to store a large, unbounded public dataset on every node. Nostr splits publishing relays from reading relays (NIP-65) and uses reconciled ID sets (NIP-77) to recover after disconnection cheaply.

**Plan:** add a signed optional peer-routing record for a key and index, with `read`, `write` and optional storage-policy capabilities; derive client's subscriptions from explicitly selected authors, spaces, groups and age windows; introduce a bounded `SYNC-RANGE` or Negentropy-like reconciliation under a versioned WebSocket capability; compare at least two independent peers where available; fetch only missing IDs and verify Ed25519. Keep user-accessible **raw** audit mode and manual full-download option, not compulsory global mirroring. Each published record should carry local durable outbox status per peer.

**Failure mode:** signed author hints can be stale, malicious or unavailable; an adversarial index may hide older messages or fake "no more results" even while returned signatures are all valid. Signed event validity is **not** proof of dataset completeness. Mitigate with multi-peer comparisons, independent signed receipts/checkpoints and conflict/omission diagnostics. Do not create one compulsory bootstrap/relay-list service.

### 2. Governance authority cannot be an accidental side effect of where a group lives

NIP-29 actually has **migration/forking**, and a forked id can legitimately represent different groups on different relays; that is useful. But its normal access authority is enforced **by a specific hosting relay** and its admins. That is exactly where WEB9000 must be stricter: group identity should be a signed charter hash, membership/change authority should follow quorum-verified signed histories, and a public namespace should remain writable by anyone through willing raw peers. A child moderation group may earn a *voluntary* specialty contract (e.g. spam classifier, scam screening, malware hashes) from a parent, but cannot gain global write veto or extort the namespace.

**Plan:** versioned proposal eligibility by independently earned group karma and **ratified-membership tenure**; immutable, proof-carrying membership decisions; a bounded scoped delegation DAG with independent signer/mandate, expiry, evidence, subject type, appeal, inherited policy semantics and cycle detection. Reader-selected fork and local moderation remain non-negotiable.

**Failure mode:** an inherited classifier or tiny high-karma council quietly becomes a veto power, or a group with stale members can be taken over by one active faction. Counter with independent ballot inclusion proofs, special constitutional safeguards, checkable approval quorum, challenge windows and explicit fork/override UI. Do not identify 'credible author' solely by money/stake.

### 3. Content-addressed media and safety decisions must remain independent

Blossom addresses bytes by SHA-256 and advertises alternative storage hosts through signed public metadata. WEB9000 already has stronger native IPFS/UnixFS capabilities for chunked audio/video and explicit volunteer mirrors. But browser clients currently trust gateway bytes to match a CID; while raw SHA-256 is easy to validate, a UnixFS CID identifies a DAG root whose digest is **not** simply SHA-256(file bytes). Local HTTP quarantine alone may not prevent P2P block exchange.

**Plan:** sign an optional *raw file SHA-256* alongside existing CID, MIME, size and primary-media metadata; browser verifies bytes before using a third-party gateway for media where feasible; keep video seek as explicit chunk verification rather than downloading full files by default. Expose provider-supplied independent blob metadata, multi-node liveness and optional Blossom compatibility without auto-upload or pin. Audit libp2p block-serving quarantine. User opts into each media host and can inspect refusal reasons.

**Failure mode:** an untrusted link or provider advertisement becomes automatic browser media retrieval, accidentally cached illegal bytes, or a quarantined CID remains accessible by alternate transport. Fix permission defaults first (an implicit peer suggestion **must never become an approved gateway**), implement serving-layer refusal and independent legal-risk review. No global delete API.

## Threats that Nostr's ecosystem illustrates, not that it solves automatically

- **Discovery centralization:** even decentralized signatures need discoverability. A single famous relay index/monitor/website or group key can become a bottleneck, a covert suppression gate, or a lucrative first-registration prize.
- **Spam migration:** open relays get spam; private or paid relays get exclusivity and membership economics. A group-specific earned-credibility proposal gate is preferable to an unrestricted global karma dictator, but it still risks incumbents colluding to reject newcomers. Use explicit appeal and transparent thresholds.
- **Opaque missing history:** a valid signature does not certify that a relay exposed every valid event. A signature proof of *some* approvals does not prove the latest decision; monitor alternate forks and build per-epoch checkpoints.
- **Reputation abuse:** signed negative claims can be manufactured at scale. NIP-56 warns of readily gamed reports, suggesting voluntary trusted report channels instead of automatically following raw report counts. For WEB9000, independent multi-source evidence, cap/decay, anti-brigade, subject-specific scopes and reviewable reversals are essential.
- **Key custody:** host-site apps are not inherently trusted merely because event IDs and signatures travel with messages. A user-controlled signer and capability-limited signing requests are the more important defense than encryption-at-rest alone.
- **No universal memory:** NIP-09 deletion requests can cause individual relays to delete or hide copies, but not guarantee removal from the network. Availability also requires actual willing retention, backups and lawful operator controls.
- **Encrypted social graphs can still leak:** private lists/DM contents do not automatically conceal relay IP, timing, login/session, or contact-relationship metadata. Use client opt-in and safety review before group activism privacy claims.

## Proposed experiments, in practical order

1. **Immediate:** adversarial replay test: third-party OrbitDB writer inserts invalid records directly into raw DB (bypasses `openPublicIndex.publish` wrapper); make acceptance/per-resource limits explicit. Separately test quarantined UnixFS retrieval directly from another libp2p IPFS peer, not only HTTP.
2. **Immediate:** peer-suggestion consent regression; no unapproved media host enters active candidate pool before user Connect. The browser should show *suggested* vs *connected* vs *approved media* separately.
3. **Soon:** add a small optional filtered `SYNC` query with `spaces/authors/kinds/after`, page continuation and bounded tests, then compare two disjoint mirrors for missing events. Evaluate NIP-77/reference Negentropy *after* simple filters prove useful.
4. **Soon:** media integrity fixture verifies correct raw SHA-256 and detects a gateway returning swapped bytes for an IPFS CID, with distinction for UnixFS root vs raw bytes.
5. **Soon:** a signed local-only `relay-list`/provider-hint proposal with explicit user consent. Pair it with independently observed health, and test two gateway failures and safe fallback.
6. **Next governance milestone:** only propose/approve **proposal-initiation policy schema** after tests for small active groups, large dormant groups, newcomer discrimination, karma rings, and takeover attempts. Keep voting democratic and quorum snapshots explicit.
7. **Later:** a reversible translation/export layer for Nostr kinds/Blossom without weakening WEB9000's own signed event version, binary IPFS CID semantics, group authority or local moderation.

## Implementation warning: protocols are NOT wire-compatible

WEB9000 events are **Ed25519**, domain-separated over `WEB9000/event/v1` and a canonical object hash; Nostr `NIP-01` uses Schnorr/secp256k1 and its own JSON-array serialization. You cannot publish a WEB9000 signed `{id,payload,signature}` to an unmodified Nostr relay as if it were a native NIP event, nor can you verify a Nostr signature using WEB9000's `verifyEvent`. Interoperation requires explicit **dual-signing or translation with provenance**, distinct keys or audited key derivation, and a decision about whether to preserve source signatures as nested evidence. Do not make translation a new authority on group validity or silently coerce event semantics.

## Additional Nostr developments relevant to WEB9000 (checked November 2026)

The following NIPs further clarify how to avoid inventing an unsafe trust oracle. None should become mandatory global authority.

- **[NIP-85 Trusted Assertions](https://nips.nostr.com/85)** publishes signer-attributed, replaceable assessments of subjects (keys, events and addressable events), and lets a person specify preferred assessment providers. **Useful pattern:** group-specific, source-tagged karma attestations signed by independent evaluators, with a snapshot/provenance/reference to the actual scoring inputs and appeals; the reader chooses which assessors count. **Failure mode:** turning the most popular NIP-85-like scorer into an unappealable, indispensable gatekeeper. Provider-computed `rank` is a *claim* and cannot alone establish earned group-karma, membership duration or eligibility. NIP-85 permits paid-relay access, so avoid making premium attestations a mandatory subscription for public raw publishing.
- **[NIP-67 EOSE completeness hints](https://nips.nostr.com/67)** (a 2026 draft) gives relays optional `finish`/`more`/`auth` hints for their own filtered event sets, because the previous EOSE boundary did **not** tell clients whether a relay silently truncated history. **Useful pattern:** after a paginated `SYNC`, return an explicit bounded `more` status and cursor; do not call a collection complete because a last page was short. **Critical distinction:** a relay's `finish` is a *self-assertion about its own retained records*, not proof no other independent peer holds additional records or forks. Byzantine omission still needs cross-peer reconciliation and signed checkpoints.
- **[NIP-48 bridged event provenance](https://nips.nostr.com/48)** carries a `proxy` reference to the original non-Nostr object. **Useful pattern:** when importing Nostr/ActivityPub material into WEB9000, preserve source protocol, original event ID, source signed envelope where allowed, original author key mapping and importer attestation. Imported content should remain visibly **bridged**, never appear cryptographically signed by the original author under a newly forged WEB9000 identity. Consider duplicate-collapse only after provenance verification.
- **[NIP-5a static websites / nsites](https://nips.nostr.com/5a)** defines signed path-to-SHA256 manifests, source links, aggregate hashes and immutable site snapshots with optional Blossom providers. **Useful pattern:** self-hostable WEB9000 client builds can be pinned by signed deterministic **versioned frontend manifests**, independently mirrored and diffed, reducing dependence on a compromised static host. **Hard problem:** signing a manifest does not make malicious injected JavaScript safe, and a new install still must authenticate which software publisher/key and build it trusts. Prefer reproducible builds and user-controlled signing keys.
- **[NIP-03 OpenTimestamps for Nostr events](https://nips.nostr.com/3)** demonstrates externally anchored hash time evidence, but the source currently explicitly labels NIP-03 **unrecommended** and warns of a specific unresolved attack. **Do not implement NIP-03 by rote as WEB9000's final vote clock.** Independent or blockchain timestamp attestations might prove a record existed *no later than* an anchoring event, but do not prove all voters could see it, that all valid ballots were included or that a governance fork is unique. Explore native audited notarization plus challenge and visibility windows instead.

**Research priority update:** For karma, investigate NIP-85-like **user-selected, source-attributed assertions**; for robustness, pair NIP-77 reconciliation with NIP-67-style explicit pagination completeness hints; for static hosted app key safety, evaluate signed release manifests (NIP-5a concept) alongside an isolated signer (NIP-46 concept). None of these eliminates the need for independent verification of proposal eligibility or human activity.
